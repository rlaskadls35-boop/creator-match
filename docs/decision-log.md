# 결정 기록 (Decision Log)

> 이 문서는 변경 과정을 보존한 기록입니다. 이후 결정으로 대체된 내용이 포함되어 있습니다. 제출 시점의 실제 동작과 최종 비중·규모·신규 후보 처리는 루트의 [README](../README.md), [PRD](../PRD.md), [flowchart](../flowchart.md)를 기준으로 확인해 주세요.

브레인스토밍과 구현 과정에서 내려진 결정을 시간순으로 남긴다. 각 항목은 "AI(Claude Code)가 무엇을 제안했고, 사용자(김태홍)가 어떻게 판단해 무엇으로 결정됐는지"를 적는다. AI_USAGE.md를 쓸 때 이 파일을 근거로 삼는다.

표기: **AI** = Claude Code 제안, **사용자** = 지원자 판단, **결과** = 최종 결정.

## 2026-09-11 (브레인스토밍 1일차)

### L01. 진행 방식: 질문 도구 대신 채팅
- AI: 선택지를 UI 질문 도구(AskUserQuestion)로 제시
- 사용자: "질문 도구 사용하지 말고 채팅으로 진행하자"
- 결과: 모든 질문·선택지를 채팅 텍스트로. 이후 세션에도 적용되도록 메모리에 저장

### L02. 데이터 프로파일링 선행
- AI: CSV를 그대로 쓰지 않고 먼저 전수 분석 (BOM·CRLF, 공란 27건 = 캠페인 0건 27명 동일 집단, avg_campaign_budget ≠ total/count, 팔로워 분포의 빈 구간, 구간별 단가 비겹침, 참여율-팔로워 음의 상관, 희소 조합)
- 사용자: 분석 결과를 근거로 이후 결정 진행
- 결과: 설계 문서 3.2절의 근거가 됨

### L03. 예산의 의미
- AI: 3안 제시 (1인 캠페인 예산 / 총예산 / 둘 다) + 1안 추천
- 사용자: "크리에이터 1인 캠페인 예산이 맞아"
- 결과: D1. 총예산 배분은 범위 밖으로 명시

### L04. 이력 없는 크리에이터 처리 (1차)
- AI: 3안 (한 리스트에서 보수적 추정 / 별도 구역 / 체크박스 제외) + 1안 추천. 단, 1안 설명이 어려워 사용자가 "이해하기 쉽게 다시" 요청 → 예시로 재설명
- 사용자: 단가 추정은 납득. 단, **"평점을 임의로 산정해서 별점을 주는 건 아니라고 생각해. 0점을 주면 어떤 부작용이 있는지 말해줘"**
- AI: 실제 데이터로 시뮬레이션 (0점: 신규 27명 전원 141~200위, 실제 최저 평점 3.4점인 사람들보다도 아래 / 평균 채움: 60위까지 / 항목 제외+감점: 85위까지) 표로 제시. 화면에 가짜 별점을 그리지 않는다는 점은 사용자 지적이 맞다고 인정. 대안으로 "평점 항목 제외 + 미검증 감점" 제안
- 사용자: 설명을 다시 듣고 **"예상 평점이라는 배지를 두면 광고주가 판단하기 오히려 좋다. 마우스 오버 툴팁으로 산정 근거를 알리자"**
- 결과: D11. 예상 평점 배지 + 툴팁. "추정치는 항상 라벨 + 툴팁" 원칙이 예상 단가에도 적용됨 (D12)
- AI_USAGE 관점: AI가 처음 제안한 "계산에만 쓰고 화면엔 평점 없음"보다 사용자의 "예상이라 밝히고 보여주기"가 광고주 판단에 더 유리하다고 판단한 사례

### L05. 참여율의 의미 확인
- 사용자: "참여율이 크리에이터가 캠페인에 참여하는 비율인지, 구독자의 참여율인지?"
- AI: 구독자(시청자) 참여율. 값 범위(3~8.9%)와 팔로워와의 음의 상관(−0.59)이 그 해석을 뒷받침
- 결과: 용어 확정. PRD 용어 정의 후보

### L06. 팔로워 구간 기준
- AI: 1만/10만 컷 제안 (업계 관행 + 데이터 빈 구간 + 단가 비겹침)
- 사용자: "통상 기준이 정말 그런지 웹에서 검색해서 말해봐"
- AI: 국내외 8개 자료 확인. 나노 <1만, 마이크로 1만~10만, 매크로 10만~100만, 메가 100만+ 로 일치. 공식 표준은 없음
- 사용자: "PRD에 '실서비스라면 100만 이상 분리한다'라고 적지 마"
- 결과: D5. 메가는 해당자 없어 제외한 사실만 기재
- AI_USAGE 관점: AI 주장을 그대로 받지 않고 외부 검증을 요구한 사례

### L07. 문서 내용 승인 규칙
- 사용자: **"PRD에 적을 내용을 임의로 정하지 말고, 무엇을 어떻게 적을지 내 확인을 꼭 받아라"**
- 결과: D30. 문서마다 항목별 초안 목록 → 승인 → 작성. 메모리에 저장

### L08. 점수 항목 5개
- AI: 과제가 명시한 4개(참여율·조회수·평점·건수) + 비용 효율 1개
- 사용자: 5개 동의. 단, "비용 효율"에 대해 **"평균 조회수 ÷ 단가라면 실측이 아니라 평균 기반이니 '평균 비용 효율'이 맞지 않나?"**
- AI: 맞는 지적. 계산식에 먼저 눈이 가서 사용자에게 어떻게 읽힐지를 놓쳤다고 인정. 이름 2안 제시
- 사용자: "조회 1회당 평균 비용"으로. 이어 "왜 이 항목을 추천했나?" → AI가 근거(예산 필터는 이하/초과만 보므로 같은 예산 안의 효율 차이를 못 잡음. 실제 데이터에서 22원 vs 146원 6배 차이) 와 반대 논거(과제 명시 항목 아님, 조회수와 일부 중복) 를 함께 제시
- 사용자: 넣기로 결정. 계산식(700,000 ÷ 8,279 = 84.6원) 확인
- 결과: D6. 이름 "조회 1회당 평균 비용", 낮을수록 좋음
- AI_USAGE 관점: 업계 용어(CPV/비용 효율)를 그대로 쓴 AI 표현을 사용자가 "추정치임이 드러나야 한다"고 바로잡은 사례. L04와 같은 원칙

### L09. 비교 방법 (백분위, 비교 집단)
- AI: 항목별 "상위 몇 %" 변환. 참여율·조회수·비용은 같은 규모 안, 평점·건수는 전체
- 사용자: 여러 차례 "이해 안 간다" → AI가 학교 등수, 수능 백분위 비유로 재설명. "광고주 입력 필터와 전체 기준 등수가 상충하지 않나?" → 필터(누구를 보여줄지)와 등수(각자가 얼마나 좋은지)는 별개이며, 결과 안에서 등수를 매기면 후보 1명이 항상 상위 1%가 되는 문제가 있음을 설명. "카테고리는 비교 집단으로 안 쓴다"의 뜻도 재설명(칸이 1~2명이 되어 등수 무의미)
- 결과: D7
- AI_USAGE 관점: 사용자가 이해될 때까지 반복 질문한 구간. 최종적으로 사용자가 "면접에서 말로 설명할 수 있는 수준"을 요구 → AI가 30초 설명과 예상 질문 답안을 정리

### L10. 합산 점수 이름
- AI: "추천 점수" 추천, 대안 "매칭 점수", "종합 점수"
- 사용자: "매칭 점수가 더 나은 것 같아"
- 결과: D8. AI 추천안이 아닌 사용자 선택

## 2026-09-12 (브레인스토밍 2일차)

### L11. 비중 결정 방식: 운영자 슬라이더
- AI: 비중 30/25/20/15/10을 코드 기본값으로 제안
- 사용자: **"비중을 관리자 화면에서 슬라이더로 직접 조절하고 결과를 보면서 정하자. 로그인 환경을 만들고 사용자 화면에서는 조절이 보이지 않게"**
- AI: 아이디어 채택. 단, 로그인은 정적 사이트라 진짜 인증이 불가하고 가짜 로그인은 감점 위험이라며 반대
- 사용자: **"평가자는 로컬에서 실행해 볼 거고 라이브 서비스가 아닌데 왜 안 되나?"**
- AI: 입장 수정. "보안 장치"가 아니라 "두 역할이 있다는 화면 구성"으로 보면 의미가 있고, "프로토타입용 임시 계정"이라고 명시하면 오해가 없다고 판단. 목업 로그인 제안
- 결과: D23, D24. 사용자 아이디어 + AI의 한계 명시(브라우저 저장소에만 유지, 실제 인증 아님)
- AI_USAGE 관점: AI가 과도하게 반대한 것을 사용자가 논리로 뒤집은 사례

### L12. 광고주 화면에 비중 표시 여부
- AI: 점수 막대 옆에 비중을 읽기 전용으로 표시 제안 (설명 가능성 가산점)
- 사용자: "광고주 화면에는 보여줄 이유가 없다"
- 결과: D10

### L13. 평점 보정(소수 표본 축소) 제거
- AI: 캠페인 1~3건인 사람의 평점을 평균 쪽으로 당기는 보정 제안. 계산식 설명(가상 캠페인 3건)
- 사용자: 설명이 어려워 두 번 재요청. 이해 후 **"왜 평점을 굳이 평균으로 보정해야 하나? 1건에 5.0이면 광고주가 그걸 보고 판단하면 되는 것 아닌가? 과제의 예외 처리 요구 때문인가?"**
- AI: 두 가지를 분리해 답변. (가) 공란 평점 → 4.4 채움은 과제의 Null Safety 요구 (0은 "최악", 공란은 "모름"이라 다름). (나) 보정은 AI가 덧붙인 것이며 과제 요구 아님. 재검토 결과 캠페인 건수가 이미 점수 항목(10)에 있어 "1건 5.0이 30건 4.8을 이기는 문제"를 이미 막고 있음 → 이중 처리. **보정 제거로 제안 변경**
- 사용자: "4.4는 왜?" → AI: 데이터의 실제 평균이며 0/2.5/5와 비교표로 이유 설명. 사용자 "평점 없는 사람들에게 인식값을 부여하는 거지?" → 맞음
- 결과: D11(예상 평점 4.4 유지), D14(보정 없음)
- AI_USAGE 관점: 사용자 질문으로 AI가 자기 제안의 불필요함을 발견해 철회한 사례. 설명 단순화 효과

### L14. 후보 0명 화면

### L15. 추천 근거 표시

- 사용자: "관리자 슬라이더를 조절하면 유의점도 바뀌나? 그 로직도 설계에 들어가나?"
- AI: 비중은 합산에만 쓰이고 항목 점수·칩·유의점·배지는 데이터로만 결정 → 순위·점수는 바뀌지만 유의점은 불변. 극단 비중 시 순위 이유와 강점 칩이 어긋날 수 있는 한계와 대안(기여 점수 기준 칩)의 단점 설명
- 사용자: 유의점 유지 확정
- 결과: D17, D25

### L23. 운영자 화면 UX 개선안(admin-ux-proposal.html) 반영
- 사용자: 외부에서 만든 운영자 화면 개선안 HTML을 두고 **"제안서대로 우리 UI/UX를 수정하고 반영하도록 해"**
- 확인받은 것: 미리보기 갱신 규칙. 지금까지는 L21 결정대로 합이 100이 아니어도 **비율 환산**해 실시간 반영했는데, 제안서는 **합계가 정확히 100일 때만 갱신**. 두 안의 체감 차이를 설명하고 물은 결과 → **제안서대로(A안)**. L21의 3번 결정을 뒤집음
- 반영한 것
  1. 비중 입력: 슬라이더 + 숫자 칸(0~100 정수) + −/+ 버튼, 항목마다 "반응이 높은 채널을 우선" 한 줄 설명
  2. 합계 안내: "합계 N% / 100%"와 함께 "12% 초과 · 비중을 낮춰 100%를 맞추세요" 식으로 다음 행동을 지시
  3. 저장 영역: "저장된 기준 / 저장하지 않은 변경" 상태 + [기본값] [변경 취소] [비중 저장]. 변경이 없으면 저장·취소 비활성
  4. 결과 위에 "미리보기 조건(예산·카테고리·규모)" 줄과 "저장된 비중으로 계산 / 변경한 비중으로 미리보기 · 저장값과 비교 / 미리보기 갱신 대기" 상태 문구
  5. 결과 표: 저장값 대비 점수 차이(+19.5점 / 저장값과 동일)와 순위 변화("2위에서")
  6. 운영자 펼침을 "왜 추천하나요?"에서 **매칭 점수 계산 내역** 표로 교체 — 항목별 실제 수치·계산 기준 / 항목 평가(100점)와 등수 / 반영 비중 / 매칭 점수에 반영된 점수, 상단에 "합산 56.6점 · 최종 표시 57점". 캠페인 0건 행은 강조하고 "0건인데 6.5점인 이유"를 접이식으로
- 제안서와 다르게 판단한 것(모두 사용자에게 알림)
  - 제안서에는 검색 입력이 없지만(시안이라 조건 고정), 운영자는 조건을 바꿔 시험해야 하므로 **검색 패널 유지** + 조건 요약 줄만 추가
  - 계산 내역은 비중을 드러내므로 **운영자 화면 전용**. 광고주 펼침은 "왜 추천하나요?" 그대로 (L12·D10 유지)
  - 매칭 점수 막대는 제안서에 없지만 광고주 화면과 공통이라 **유지**하고 점수 아래 변화량만 추가
  - 좁은 화면(767px 이하)에서 결과 표를 **카드로 접어** 가로 스크롤 제거. 이때 머리글 정렬 버튼이 사라지므로 결과 줄에 정렬 선택 + 방향 버튼을 추가(좁은 화면에서만 노출)
  - 등수 표기에 동점 여부 반영: "전체 200명 중 **공동** 174등". 광고주 화면 막대에도 같이 적용(같은 데이터에 두 표기가 생기지 않도록)
- 함께 제거·정리: `normalizeWeights`(비율 환산) 삭제, 테스트 정리 훅(`afterEach(cleanup)`) 추가


### L24. 신규 후보 별도 표와 네 지표 점수 — 로컬 검토안
- 사용자: 이력·평점·단가가 없는 후보가 추정값을 근거로 1위에 오르는 것이 납득하기 어렵다고 지적. 두 표로 구분하는 제안을 확인한 뒤 **"로컬에서 확인하게 로컬에다가 구현해봐 깃에다가는 아직 push 하지 말고"**라고 요청.
- AI(Codex): 캠페인 건수는 성과와 같지 않으므로 점수에서 제외하고 경험 정보로 남김. 조회당 비용은 같은 조회수에서도 비용 차이를 보여주므로 유지. 신규에게 평균 평점·단가를 채워 종합점수를 부여하던 방식 제거.
- 로컬에 반영:
  1. 상단: 실제 평점·과거 평균 단가가 있고 입력 예산·카테고리·규모에 맞는 이력 있는 후보만 종합순위로 표시.
  2. 하단: 카테고리·규모가 맞는 신규 후보를 별도 표에 표시. 참여율 또는 평균 조회수로 정렬하며, 종합점수와 통합순위는 없음.
  3. 신규 평점·단가·조회당 비용은 null로 유지. 평점은 '없음', 단가는 '확인 필요'. 규모별 중앙값은 참고 단가로만 표시하며 예산 통과 판정이나 점수에 사용하지 않음.
  4. 신규 후보는 단가가 없으므로 예산만으로 포함/제외하지 않음. 예산 충족 여부 미확인을 명시. 기존 후보 0명이어도 신규 표는 표시. 플랫폼 필터는 양쪽 표에 적용하고 이력 있는 후보만 체크하면 신규 표 숨김.
  5. 점수 네 항목: 참여율·평균 조회수·광고주 평점·조회당 비용. 캠페인 건수는 표와 정렬에만 남기고 비중·추천 근거 막대·계산 내역에서 제외.
  6. 최종 네 비중은 미확정. 신규 정책의 효과를 먼저 비교할 수 있게 기존 30:25:20:15 비율을 정수 합계 100으로 환산한 **33/28/22/17**을 임시 기본값으로 사용. 기존 브라우저 저장값은 건수만 빼고 나머지 비율로 환산하여 읽음. 사용자 저장 전 원래 저장값을 덮어쓰지 않음.
  7. 참여율·조회수의 비교 집단은 기존 규모 전체 유지. 평점·비용은 결측값을 제외한 기록 있는 집단으로 비교. 원본 CSV 변경 없음.
- 확인: 테스트 85개 및 프로덕션 빌드 통과. 신규 점수 미생성, 건수 변경에 대한 점수 불변, 예산 미확인 처리, 두 표·플랫폼 필터·운영자 미리보기 검증. Codex 로컬 브라우저에서 50만 원·뷰티·나노의 기존 2명/신규 1명과 데스크톱·좁은 화면 배치 확인. Git push는 수행하지 않음.

### L25. 검색 조건 압축·플랫폼 선적용·비중 조절 접기

  2. 플랫폼을 검색 전 조건으로 이동. 기존·신규 후보, 미리보기 조건, 0명 진단, 근접 후보, 조건 완화에 같은 플랫폼 기준을 적용.
  3. 특정 플랫폼에서 후보가 없거나 적을 때 `플랫폼을 전체로 넓히면 → N명` 완화 선택지를 추가.
  4. 매칭 점수 비중 카드는 기본으로 접어 현재 네 비중과 저장 상태만 보여주고, `비중 조절`을 누르면 기존 상세 조절·저장 UI가 펼쳐지도록 변경.
  5. 시안의 임의 결과 테이블·페이지네이션은 구현하지 않고 실제 CSV 기반의 기존 결과 테이블을 그대로 유지.

### L26. 후보 0명 화면에서 진단 문단과 조건 완화 버튼 제거
- 사용자: 0명 화면에서 완화 버튼이 "예산/규모 2개/카테고리" 네 개로 고정 노출되는 로직을 문제 삼음. 실제로 뷰티·나노·10만 원에서는 4개 중 3개가 0명(비활성)이라 읽을 거리만 늘고 판단에 쓸 수 없음. **"이 두 UI는 제거하는 게 맞는 것 같다"** — 진단 문단 카드와 완화 버튼 묶음 모두 제거 지시. 근접 후보 표는 유지, 신규 후보 표는 이후 논의.
- 반영:
  1. 0명 화면 = 결과 줄("캠페인 이력이 있는 후보 0명") + 근접 후보 표 + 신규 후보 표. 진단 문장(`diagnosis`/`extraNote`)과 이를 만들던 `diagnoseZeroResult`, 0명 화면 전용 컨테이너(`ZeroResults`), 관련 CSS 제거.
  2. 완화 버튼 생성 로직(`buildRelaxations`)과 버튼 UI(`RelaxationList`)는 **후보 1~2명 화면에서만** 계속 사용. 0명 화면에서는 호출하지 않음.
  3. 근접 후보마저 없을 때(조건이 두 개 이상 어긋난 사람만 있는 경우) 화면이 비지 않도록 한 줄 안내를 남김: "조건에 가까운 크리에이터도 없습니다. 예산·규모·카테고리를 바꿔 다시 찾아 보세요."
- 트레이드오프: "왜 없는지"를 설명하던 문장과 "규모·카테고리를 바꿔도 안 된다"는 근거가 사라짐. 대신 화면이 여섯 덩이에서 세 덩이로 줄고, 남은 근접 후보 표가 곧 대안 제시 역할을 함(과제의 "빈 화면 방치 금지" 요건은 이 표로 충족).
- 확인: 테스트 85개·프로덕션 빌드 통과. 0명 화면 테스트를 "진단 문단·완화 버튼이 없고 근접 후보 표만 있다"로 바꾸고, 완화 버튼 클릭→폼 반영→재검색 테스트는 후보 1명(뷰티·매크로·310만 원) 화면으로 옮김. 로컬 브라우저에서 뷰티·나노·10만 원 화면 확인.

### L27. 원본 CSV 보존과 SQLite 데이터 로드 (2026-09-12)
- 사용자: 과제에 맞게 CSV 원본을 훼손하지 않고 DB를 SQLite로 설정해 달라고 요청. 원본 유지, 별도 SQLite 생성, 기존 화면·추천 결과·GitHub Pages 유지, 일치 검증 계획에 **"ㅇㅇ 진행해"**로 승인.
- AI(Codex): 원본 11개 필드를 `data/creators.sqlite`의 `creators` 테이블에 저장하고 평점 공란 27개는 SQL NULL로 보존. DB 버전·인원·원본 SHA-256을 함께 관리한다. 원본 두 CSV는 읽기만 하며, 제공 당시 SHA-256과 다르면 DB 생성을 중단한다.
- 실행: 기존 `npm run dev`, `npm run build`, `npm test`, `npm run test:watch` 전에 DB를 자동 준비한다. `npm run db:build`로 별도 재생성할 수도 있다. 같은 데이터로 재실행해도 중복이 생기지 않고 동일한 DB는 다시 쓰지 않는다. SQLite 생성 시 무결성 및 원본 200명 전체 필드·파생값·통계 일치를 검증한다.
- 화면: CSV 직접 로드에서 sql.js를 통한 SQLite 읽기 전용 SQL 조회로 전환. 기존 점수·추천·신규 후보 분리 규칙은 재사용한다. 로드 중 안내와 실패 시 다시 시도 버튼을 제공한다.
- 범위와 트레이드오프: 크리에이터 조회용 DB 전환이다. 브라우저가 SQLite 파일과 WASM을 같은 사이트에서 받아 메모리에서 조회하므로 서버 없이 GitHub Pages에서 실행할 수 있다. 최초 접속 시 WASM 다운로드가 추가된다. 운영자 비중과 임시 로그인 세션은 기존 localStorage를 유지하며, 여러 사용자 사이에서 공유되는 서버 DB나 쓰기 API는 도입하지 않는다.
- 확인: 자동 테스트 97개·프로덕션 빌드 통과. 원본 두 CSV의 SHA-256 일치, SQLite 무결성, 200명·NULL 27개, 재생성 멱등성, 모든 추천 항목 점수 일치, 손상·누락·버전 오류 처리 검증. 실제 Chromium에서 개발 서버와 배포용 빌드의 SQLite/WASM 로드, 뷰티·패션·마이크로·150만 원의 이력 후보 15명 및 1위 정은매거진77, 추천 이유 펼침·평점 정렬·운영자 비중 저장·모바일 폭·로드 실패 후 재시도 확인. 외부 배포는 수행하지 않음.

### L28. 규모 경계를 1.5만 / 10만으로 조정 (2026-09-12)
